# Detection — Active Directory Security Lab

## 1. Objective

The objective of this module is to inspect Windows Security events and learn how to distinguish expected Active Directory authentication activity from events that require further investigation.

The assessment uses read-only event-log queries on the lab domain controller, DC01.

## 3. Practical: Query Authentication Events

The following PowerShell command was used to retrieve selected authentication-related events from the previous 24 hours:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4624, 4625, 4768, 4769, 4771
    StartTime = (Get-Date).AddHours(-24)
} -MaxEvents 30 |
Select-Object TimeCreated, Id, ProviderName, Message |
Format-List
```

The query is read-only. It retrieves up to 30 matching events, not necessarily every matching event in the time range.

## 5. Understanding Relevant Event IDs

| Event ID | Meaning | Investigation focus |
|---|---|---|
| 4624 | Successful logon | Account, logon type, source, authentication package |
| 4625 | Failed logon | Account, source, failure reason, repeated attempts |
| 4768 | Kerberos TGT requested | Requesting account, client address, result code |
| 4769 | Kerberos service ticket requested | Account, requested service, client address, encryption type |
| 4771 | Kerberos pre-authentication failed | Account, client address, failure code |

Event generation depends on audit policy, Windows configuration, and the activity performed.

## 6. Important Logon Types

| Logon type | Meaning |
|---|---|
| 2 | Interactive logon |
| 3 | Network logon |
| 5 | Service logon |
| 10 | RemoteInteractive, commonly Remote Desktop |

A logon type must be interpreted in context. For example, a Type 3 logon can be generated by legitimate SMB or other network activity.

## 7. How to Investigate a Potentially Suspicious Event

For each event of interest:

1. Identify the account and determine whether it is a user or computer account.
2. Record the timestamp and source IP when available.
3. Identify the logon type and authentication package.
4. Check whether the source system and destination service are expected.
5. Correlate related events, such as a TGT request, a service-ticket request, and a destination logon.
6. Compare the activity with the lab's expected behavior.
7. Record the evidence and uncertainty before reaching a conclusion.

A single event ID, elevated-token field, or successful authentication is not sufficient to establish malicious activity.

## 9. Limitations

- The supplied output is truncated.
- The query returns a maximum number of matching events, so it is not an exhaustive log export.
- The presence or absence of an event depends on auditing configuration and log retention.
- Successful authentication does not by itself establish that the activity was authorized.
- Suspicious activity should be assessed using multiple related events and the expected lab baseline.

## 10. Conclusion

This exercise demonstrated how to query Windows Security authentication events and interpret basic logon information. The supplied evidence contains successful service and network logons involving DC01's system context and computer account.

Further conclusions require correlation with additional events and knowledge of the expected system activity. Detection should be evidence-based and should distinguish unusual activity from confirmed malicious behavior.
